# SmokingTrackerBot: постоянные проектные инструкции

## Назначение и границы репозитория

Этот репозиторий отвечает за код Telegram-бота, миграции базы данных,
воспроизводимый набор Python-зависимостей и декларативный контракт размещения в
`DEPLOYMENT.md`.

Конкретные production-хосты, абсолютные пути, пользователи ОС, unit-файлы,
backup-расписания и способ доставки релиза относятся к инфраструктурному
проекту. Не добавлять их в проектную документацию и не изменять внешнюю
инфраструктуру без отдельной задачи. `deploy/smoking-tracker-bot.service`
является примером, а не источником фактического production-состояния.

## Архитектура и обязательные инварианты

- Runtime: CPython 3.14 в отдельном virtual environment.
- Точка входа: `main.py`.
- Бот получает Telegram updates через long polling; HTTP endpoint и входящий
  порт приложению не нужны.
- Обычное текстовое сообщение создаёт запись в SQLite; `/start`, `/summary` и
  `/day` являются поддерживаемыми командами.
- Для одного `TELEGRAM_TOKEN` разрешён ровно один polling-процесс. Перед
  запуском замены или rollback необходимо полностью остановить предыдущий
  экземпляр и подтвердить завершение его процесса.
- `main.py --check` разрешено выполнять рядом с работающим экземпляром: режим
  вызывает Telegram `getMe`, но не `getUpdates` и не запускает polling.
- Единственное постоянное хранилище приложения — SQLite-файл, заданный через
  `DATABASE_URL`.

## Зависимости

- Прямые production-зависимости фиксируются в `requirements.in`.
- `requirements.txt` — сгенерированный lock-файл со всеми транзитивными
  зависимостями и hashes. Устанавливать его с `--require-hashes`.
- Lock-файл генерировать на Linux с CPython 3.14 и зафиксированной версией
  `pip-tools`; обновлять и коммитить оба requirements-файла вместе.
- Не устанавливать зависимости глобально и не редактировать сгенерированный
  `requirements.txt` вручную.

Канонические команды установки и обновления приведены в `README.md` и
`DEPLOYMENT.md`; не создавать параллельный набор инструкций без необходимости.

## Конфигурация и секреты

Приложение использует только две обязательные переменные:

- `TELEGRAM_TOKEN` — секретный токен Telegram-бота;
- `DATABASE_URL` — обычный путь к SQLite-файлу либо URL вида `sqlite:///...`.

Не читать и не выводить значения production-переменных без необходимости. Не
помещать токены, содержимое `.env`, пользовательскую базу, приватные ключи или
backup-файлы в Git, логи, команды или документацию. `.env` и `db.db` должны
оставаться исключёнными через `.gitignore`; `.env.example` содержит только
безопасные примеры и имена переменных.

## SQLite, Alembic, backup и rollback

- Изменения схемы оформлять отдельными Alembic migrations. Новую базу и
  существующую базу приводить к актуальной схеме командой
  `.venv/bin/python -m alembic upgrade head`.
- Если SQLite-файл ещё не существует и создаётся новая пустая база, выполнять
  `alembic upgrade head` можно без backup отсутствующей базы и без остановки
  отсутствующего writer-процесса.
- Перед migration существующей постоянной базы или другим риском изменения её
  данных полностью остановить writer-процесс и создать согласованную
  backup-копию средствами SQLite backup API или `.backup`. До продолжения
  backup-копия должна пройти `PRAGMA integrity_check`.
- Не копировать обычным `cp` SQLite-базу, пока приложение может в неё писать.
- Каждая backup-копия должна проходить `PRAGMA integrity_check`; восстановление
  периодически проверять на отдельном временном файле.
- Не выполнять автоматический `alembic downgrade`: обратимость и совместимость
  данных оцениваются для каждого релиза. При несовместимой схеме rollback
  выполняется из проверенной backup-копии с сохранением актуальной базы для
  возможного извлечения новых записей.
- Полный порядок миграции и безопасного rollback определяется
  `DEPLOYMENT.md`.

## Проверка изменений

Перед завершением изменения запускать релевантные проверки. Базовый набор:

```bash
.venv/bin/python -m pip check
.venv/bin/python -W error::DeprecationWarning -m unittest discover -s tests -v
.venv/bin/python -m alembic current --check-heads
.venv/bin/python main.py --check
```

Последние две команды требуют настроенных переменных и доступной базы;
`main.py --check` также требует исходящего доступа к Telegram. Не раскрывать
секреты в выводе. Для тестов polling использовать отдельный тестовый токен либо
полностью остановить production-экземпляр.

После релиза вручную проверять стабильность процесса, `/start`, `/summary`,
`/day` и контролируемое обычное сообщение. Учитывать, что обычное сообщение
создаёт постоянную запись.

## Поддержка документации

- `README.md` описывает назначение приложения, пользовательское поведение и
  воспроизводимый developer workflow. Обновлять его при изменении команд бота,
  требований к Python, конфигурации, установки, локального запуска или проверок.
- `DEPLOYMENT.md` является каноническим декларативным runtime-контрактом.
  Обновлять его при изменении зависимостей размещения, переменных окружения,
  entry point, writable-путей, постоянных данных, lifecycle hooks, migrations,
  smoke-проверок, backup или rollback-совместимости.
- `AGENTS.md` хранит правила сопровождения и безопасные инварианты, но не должен
  дублировать подробный runbook из `DEPLOYMENT.md` или developer guide из
  `README.md`.
- При изменениях, затрагивающих содержание README или DEPLOYMENT, обновлять
  соответствующий документ в том же change set.

Для документационных правок проверять `git diff --check`, рабочее дерево и
отсутствие конкретных production-деталей в `DEPLOYMENT.md`.
