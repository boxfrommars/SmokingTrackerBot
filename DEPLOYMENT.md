# Требования к размещению: SmokingTrackerBot

Этот документ описывает требования приложения и проверяемый результат. Он не
задаёт конкретную среду размещения, абсолютные production-пути, пользователей
ОС, способ передачи релиза или инструмент управления процессом.

Не добавлять сюда значения секретов, содержимое production-конфигурации,
приватные ключи, базы данных или резервные копии.

## Приложение

| Параметр | Значение |
| --- | --- |
| Название | `SmokingTrackerBot` |
| Репозиторий | `git@github.com:boxfrommars/SmokingTrackerBot.git` |
| Production-ветка | `master` |
| Канонический URL | не применимо |
| Тип процесса | долгоживущий Telegram long-polling процесс |
| Runtime | CPython 3.14 |
| База данных | SQLite |

## Runtime-интерфейс

- Package manager: `pip` в отдельном virtual environment.
- Установка production-зависимостей:

  ```shell
  .venv/bin/python -m pip install --require-hashes -r requirements.txt
  ```

- Относительный публичный каталог: не применимо.
- Entry point:

  ```shell
  .venv/bin/python main.py
  ```

- Frontend-сборка: отсутствует.
- Требуемые системные возможности: CPython 3.14 с `venv`, `ssl` и `sqlite3`,
  DNS и исходящий HTTPS-доступ к Telegram Bot API, возможность корректно
  доставить процессу сигналы завершения.
- Входящий порт, HTTP-сервер, доменное имя и TLS termination приложению не
  требуются.
- Процесс должен корректно завершаться перед заменой. Для одного
  `TELEGRAM_TOKEN` одновременно разрешён ровно один polling-процесс.

Все относительные пути разрешаются от корня приложения. Среда размещения
выбирает расположение файлов, способ запуска и механизм наблюдения за процессом.

## Конфигурация

| Переменная | Обязательна | Секрет | Назначение и инвариант |
| --- | ---: | ---: | --- |
| `TELEGRAM_TOKEN` | да | да | Непустой токен Telegram-бота. Передаётся только через защищённую конфигурацию среды и не выводится в логи или команды. |
| `DATABASE_URL` | да | нет | Путь к SQLite-файлу либо URL вида `sqlite:///...`. Другие схемы не поддерживаются; относительный путь разрешается от рабочего каталога процесса. |

Приложение вызывает `load_dotenv()`, но среда размещения может передавать
переменные напрямую. Файл `.env` не является частью релиза и не должен попадать
в Git или артефакты сборки.

## Состояние и запись

- Writable-пути runtime: SQLite-файл, заданный `DATABASE_URL`, и его
  родительский каталог, где SQLite может создавать journal и другие sidecar-
  файлы.
- Генерируемые артефакты: `.venv/` после установки зависимостей и необязательные
  Python cache-файлы; они воспроизводимы и не являются постоянными данными.
- Постоянные данные: SQLite-база, заданная `DATABASE_URL`.
- Пользовательские загрузки: отсутствуют.
- Согласованная backup-копия должна создаваться через SQLite backup API или
  команду `.backup`. Нельзя заменять это обычным копированием файла, пока
  приложение может писать в базу.
- Каждая backup-копия должна вернуть `ok` для `PRAGMA integrity_check`.
  Восстановление периодически проверяется на отдельном временном файле с
  повторной проверкой целостности и ожидаемой схемы; live-база при такой
  проверке не заменяется.

## Lifecycle hooks

### Pre-activation check

- Момент выполнения: после установки зависимостей и применения требуемых
  migrations, до запуска нового polling-процесса.
- Команда:

  ```shell
  .venv/bin/python main.py --check
  ```

- Эффект: проверяет обязательную конфигурацию, существование SQLite-файла,
  `PRAGMA quick_check`, точную схему таблицы `smoking` и Telegram credentials
  через `getMe`.
- Изменяемые пути: постоянные данные не изменяются; cache-файлы интерпретатора
  не являются обязательными.
- Изменение постоянных данных: отсутствует.
- Повторный запуск безопасен: да; команда не вызывает `getUpdates` и не
  запускает polling.
- Ошибка блокирует релиз: да.

## Изменения данных

- Создание новой пустой базы и применение migrations к существующей базе:

  ```shell
  .venv/bin/python -m alembic upgrade head
  ```

- Проверка, что применены все head revisions:

  ```shell
  .venv/bin/python -m alembic current --check-heads
  ```

- Предусловия для новой пустой базы: файл базы ещё не существует и постоянные
  данные отсутствуют. Backup отсутствующей базы и остановка отсутствующего
  writer-процесса не требуются.
- Предусловия для существующей постоянной базы: writer-процесс полностью
  остановлен; средствами SQLite создана согласованная backup-копия текущей
  базы; `PRAGMA integrity_check` для backup-копии вернул `ok`; новая версия кода
  и зависимостей уже прошла автоматические тесты.
- Обратимость: автоматический `alembic downgrade` запрещён. Текущая базовая
  migration удаляет таблицу `smoking` при downgrade, поэтому несовместимый
  rollback выполняется восстановлением проверенной backup-копии.
- Ожидаемая недоступность: для новой ещё не запущенной базы не применимо; для
  существующей базы polling остаётся остановленным на время migration, проверки
  Alembic и pre-activation check.
- Совместимость старой и новой версии с данными: для каждого изменения схемы
  должна быть явно доказана. При отсутствии такого подтверждения считать версии
  несовместимыми.

## Внешнее поведение

- Канонический URL: не применимо.
- Дополнительные имена и redirects: отсутствуют.
- Health endpoint: отсутствует.
- Наблюдаемое состояние: один долгоживущий polling-процесс остаётся активным,
  не перезапускается циклически и обрабатывает Telegram updates.

Ключевые smoke-сценарии:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Проверка процесса | Активен ровно один polling-процесс, его restart counter стабилен. |
| `/start` | Бот отвечает сообщением о доступности. |
| `/summary` | Бот возвращает агрегированные количества по пользователям и дням. |
| `/day` | Бот возвращает записи текущего дня. |
| Контролируемое обычное сообщение | Бот отвечает `ok!`, а новая запись сохраняется в SQLite и видна через обычный сценарий чтения. |

Обычное сообщение изменяет постоянные данные, поэтому такой smoke выполняется
осознанно уполномоченным пользователем.

## Проверка релиза

Команды, подтверждающие готовность кода независимо от реализации размещения:

```shell
python3.14 --version
.venv/bin/python -m pip check
.venv/bin/python -W error::DeprecationWarning -m unittest discover -s tests -v
.venv/bin/python -m alembic current --check-heads
.venv/bin/python main.py --check
```

Команды Alembic и preflight требуют настроенных переменных окружения и
доступной SQLite-базы. Preflight также требует исходящего доступа к Telegram,
но не создаёт второй polling-процесс.

Дополнительные ручные проверки: выполнить smoke-сценарии из предыдущего
раздела, подтвердить сохранение записи и отсутствие конкурирующего процесса с
тем же токеном.

## Совместимость rollback

- Вернуть предыдущую версию кода без возврата данных можно только если migrations
  отсутствовали либо обратная совместимость схемы была явно проверена.
- До rollback полностью остановить текущий polling-процесс и подтвердить его
  завершение. Затем создать согласованную копию актуальной базы, чтобы сохранить
  записи, появившиеся после релиза.
- Если предыдущая версия совместима с текущей схемой, использовать актуальную
  базу. В противном случае восстановить проверенную pre-release backup-копию,
  сохранив актуальную копию отдельно для возможного извлечения новых записей.
- После возврата кода выполнить:

  ```shell
  .venv/bin/python -m pip install --require-hashes -r requirements.txt
  .venv/bin/python -m alembic current --check-heads
  .venv/bin/python main.py --check
  ```

- Не применять автоматический Alembic downgrade и не запускать предыдущий
  экземпляр, пока новый процесс полностью не остановлен.
- После запуска повторить проверку singleton-процесса и ручные smoke-сценарии.
